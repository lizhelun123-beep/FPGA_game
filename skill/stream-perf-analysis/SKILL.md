# 流式性能与新鲜度

只分析已有日志来回答一个性能问题；不连接设备、不重启进程、不改协议、阈值或检测器。新采样需要当前任务的板端授权。

## 最小分析

1. 先确定要解释的量：采集间隔、检测耗时、接收间隔、队列年龄、UI 采用率或端到端延迟。不要把不同时间基准直接相减。
2. 读取同一连接和同一启动区间的两个完整快照或一段连续日志。确认计数、单位、时间戳来源和阶段是否累计；计数回退、重连或缺行时停止计算窗口。
3. 只计算能由输入支持的结果：平均值、间隔、年龄、样本数和明确的缺失/超时。不要从累计最大值推导 P95/P99，也不要把包含关系的阶段相加。
4. 区分“没有新包”“收到无效观测”“对象暂时缺失”“超过保持期”和“断线”。画面稳定不能单独证明吞吐提高；旧场景保持必须受界限控制，不能掩盖低吞吐。
5. 先给出一个主导瓶颈和最小下一步。若现有日志不能区分候选原因，结论写 UNKNOWN，不通过增加报告解决。

## 对当前闭环的关注点

- 重点是有效 camera frame 到权威 C 会话的年龄、姿态提交频率、过期场景拒绝和实景/Godot 采用；不要把离线照片数、单次截图、粒子刷新或 UI 60 FPS 当成实时定位通过。
- generation、sequence、captured time、level 应能关联采集、检测和渲染；跨设备注明时钟域与映射。现有 `scene-v1.capture_ms` 是处理开始时间，缺少曝光时间时不报告曝光到显示的实测延迟。
- 端到端延迟、识别频率、显示频率和鼠标响应分别描述，不合并成一个“FPS”。
- 按最终方案，实体 SOURCE 已取消；分析 Mirror/Portal 的定位更新、联合标签质量、防抖提交与丢失恢复。日志中的历史阶段名如 `detect_six` 仍按真实记录解释，不据名字恢复 SOURCE 必检或静默重定义旧指标。
- 单独量化原始定位周期、稳定算法确认/滤波延迟和显示采用；A/B 比较使用同一输入、单位与时间区间，区分死区保持、受限遮挡和没有新帧。分析本身不改算法配置，实施由游戏集成任务完成。
- PC 6 s 上限属于显示保留，C 250 ms 属于场景新鲜度；两者不能相互替代。计划中的至少约 10 Hz、争取 15–30 Hz 是待测目标，不能写成当前实绩；提高界面帧率不会改善约 1 Hz 的有效输入。

## 输出

最多给出：主导瓶颈、支持它的两三个数据点、未覆盖范围、最小下一步。使用现有脚本时让结果留在终端，除非用户明确要求保存文件。
