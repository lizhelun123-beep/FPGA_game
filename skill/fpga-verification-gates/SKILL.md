# FPGA 验证门

这不是默认构建流程。只有当前源码改动或明确阻塞需要 PL 证据时才使用；不因历史报告、比赛材料或局部优化自动运行 Vivado。

## 检查顺序

1. 明确一个问题和通过条件：例如 AXI 背压下帧是否完整、RAW10/BGGR 是否正确、复位/CDC 是否丢 SoT，或 BIT/HWH 是否同源。
2. 先核对实际源、参数、约束和输入，再做静态/语法、最小仿真或 host 对照。黄金算法和现有 C 检测器保持唯一入口，不复制第二套检测器。
3. 只有前一步不能回答问题时，才考虑 OOC 或完整构建；完整构建必须是当前任务明确授权且确有必要。旧 OOC、旧制品和截图不能转签当前顶层。
4. AXI 流检查 TVALID/TREADY、SOF/EOL、TKEEP、停顿保持、连续帧和复位边界；Bayer 检查 RAW10、BGGR、裁剪/翻转奇偶和 DDR 字节顺序。不能靠下游换色或放宽 checker 掩盖错误。
5. 若涉及实现，至少保留当前配置下的时序、CDC、DRC 和资源结论；负 slack、未约束路径或未解释 CDC 保持未通过。不要无依据加入 false path/multicycle。
6. 板端下载、复位、采集和显示仍按 AGENTS.md 的当前任务授权执行；技能本身不授权。

## 与当前目标的关系

- 摄像头实时定位优先于 PL 优化。只有采集格式、帧完整性、复位/CDC 或现有显示链直接阻塞实时闭环时才改 PL。
- 板端实景/HDMI 优先复用现有 VDMA 和 CPU 合成；电脑虚拟游戏复用既有 Godot/GPU 呈现。电脑光晕或粒子不构成增加 PL 渲染器、额外 DMA、feature tap 或新跨时钟结构的理由。
- 摄像头、电脑画布与 HDMI 目标均为 1280×720；800 行旧 UI 迁移、固定逻辑光源和 Portal 三标签接入优先在现有软件入口处理，不自动触发摄像头模式、PL 或制品变更。
- 定位/光路和游戏逻辑先做 host 对照，涉及 ARM 代码时做必要编译，再判断是否需要 PL 证据。修复当前连续采集帧边界阻塞时依据 `PROJECT_STATE.md` 的最新证据选择最小观测，不重复已停止的 PARK 诊断。

## 输出

最多给出：当前问题、最小检查结果、证据路径、未覆盖项和下一步。不要创建独立验收报告、复制历史报告或为了填模板增加测试。
